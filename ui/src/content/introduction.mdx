# 序論

## Coral-BookとCarmine-Studioの役割

Coral-Book『金融工学の応用基礎』はQuartoで、数式とコードを読みながら手元で計算を再現する。Carmine-Studio『エンタープライズ金融モデル』は、複数の利用者がブラウザから共通の計算エンジンを使えるよう、操作画面と計算APIを分ける。役割は次のとおりである。

| 層 | 担当 | 役割 |
|---|---|---|
| 画面 | React と TypeScript | 入力を受け付け、APIへ非同期にリクエストを送り、返されたJSONを本文・表・グラフとして表示する。金融の計算はしない |
| API | R（httpuv） | 入力を検査し、`rmql` の関数を呼び、結果をJSONで返す |
| 計算エンジン | Rust（`rmql`） | カーブ構築、価格評価、感応度、モンテカルロなどの計算ロジック |

APIの入出力を共通にしておけば、画面の操作を改善するときは画面側を、評価手法を追加するときは計算エンジン側を中心に改修できる。たとえば円OISの章では、画面は「5年クォートを ＋1 bp」という操作をAPIへ送るだけで、カーブの再構築と7年OISの再評価はRサーバー上の `rmql` が行う。画面に表示した数値には、どの応答から描いたかを示す応答IDを付けている。

## 計算エンジンにRustを使う理由

C++でも、RAIIやスマートポインタを使ってメモリなどの資源を管理できる。ただし、それらは書き方の規約であり、規約を外れたコードもコンパイルは通る。Rustの利点は、データを誰が所有し、いつまで参照でき、どこで書き換えられるかを、所有権・借用・ライフタイムの規則としてコンパイラが検査する点にある。安全なRustの範囲では、解放済みのメモリへの参照やスレッド間のデータ競合はコンパイル時に排除される（[The Rust Programming Language, What is Ownership?](https://doc.rust-lang.org/stable/book/ch04-01-what-is-ownership.html)）。

金融モデルでは、この規則が並列化の設計にそのまま現れる。多数の債券を同じカーブで評価するとき、カーブなどの市場データは読み取り専用の参照として全スレッドが共有し、各スレッドは自分の評価結果だけを書き込む。`rmql` の自動微分では、計算グラフを記録する作業領域をスレッドごとに持ち、この作業領域は型の上でスレッド間に共有できない作りにしている。そのため、ある銘柄の感応度を計算する途中のグラフが、別のスレッドの計算と混ざることはない。Rとの接続部分では、受け渡すデータの型や変換を検査し、入力の誤りはRのエラーとして返す。

コードの保守にはCargoを使う。`rmql` は、計算の中核のクレートとRとの接続のクレートをワークスペースにまとめ、依存関係、ビルド、テスト、ドキュメント生成を `cargo build`、`cargo test`、`cargo clippy`、`cargo doc` という共通の手順で扱う（[The Cargo Book](https://doc.rust-lang.org/stable/cargo/)）。テストには、QuantLibやRで独立に計算した参照値との照合も含まれる。新しい評価手法を加えるたびに同じ手順で全体を検査できるので、モデルを増やしても既存の計算への影響を確かめやすい。

## Rによる並列計算とSlurmへの拡張

多数の銘柄を同じ市場データで評価する場合や、独立した金利シナリオを一括計算する場合は、仕事を分けて実行できる。単一の計算機では、`future::plan(future::multisession)` と `furrr::future_map()` を使い、複数のRプロセスに評価を割り振る（[furrr](https://furrr.futureverse.org/)）。各ワーカーが同じ `rmql` の評価関数を呼び、Rが結果を集約する。

```r
future::plan(future::multisession, workers = 4)

valuations <- furrr::future_map(
  split(bonds, bonds$issue_id),          # 銘柄ごとに仕事を分ける
  \(bond) value_bond_on_curve(bond, curve),  # rmql を呼ぶ自作の評価関数（例）
  .options = furrr::furrr_options(seed = TRUE)
) |>
  dplyr::bind_rows()
```

Rust側でも並列化できる。`rmql` の債券の一括評価は、件数とスレッド数を指定して1回の呼び出しで評価し、結果はスレッド数によらず同じになる。モンテカルロの乱数も、シード・パス・次元だけで決まる方式にしているので、スレッド数を変えても同じ価格になる。Rのワーカー数とRustのスレッド数を両方使う場合は、両者の積が計算機のコア数を超えないように調整する。Carmine-Studioの「並列計算」の章では、債券の件数とスレッド数を選んで、Rサーバー上で評価時間を測れる（実装済み）。

複数の計算機へ広げる場合は、`future.batchtools` の `batchtools_slurm` を通じて、同じ評価関数をSlurmのジョブとして実行できる（[future.batchtools](https://future.batchtools.futureverse.org/reference/batchtools_slurm.html)）。`furrr::future_map()` を使った評価関数を再利用し、Slurm向けの実行方式に切り替えられる。SlurmはいまのCarmine-Studioには未導入で、ここに書く構成は将来の構想である。この構成なら、専用の高価なグリッド製品を前提とせず、既存の計算機やクラウド上のノードを使って、ジョブの待ち行列やCPU・メモリの割り当てを備えた分散計算基盤へ広げられる。そのために、クラスタの設定、各ノードへの実行環境（Rと `rmql`）の配備、入力データの受け渡しを整える。

## 非同期のWeb画面と金融業務のGUI

ブラウザからの計算リクエストは非同期に扱う。利用者は、結果を待つ間も表示済みの表を見たり、次の入力を準備したりできる。入力を続けて変えた場合は、最後の入力に対する応答だけを表示に使う。「分散計算」では、ブラウザがシナリオを複数のリクエストに分け、単一のR APIへ送り、応答を集約する。画面にはリクエストごとの処理状況と所要時間を表示する（実装済み）。複数ノードへの配分や、サーバー側でのバックグラウンド実行は今後の拡張である。バックグラウンド実行にすれば、受付・実行中・完了・失敗の状態を画面で確認し、完了後に結果を取り込める。

Carmine-Studioでは、操作性の参考例として、一部の表やグラフをインタラクティブに操作できる形で提供している。たとえばイールドカーブの章では、年月スライダーで表示月を選び、再生ボタンでカーブの形の変化を追える。静的な図では時点ごとのカーブを並べて比較するが、ここでは一つのグラフの上で時点を切り替える。カーブの構築はRサーバー上の `rmql` が行い、画面は受け取った月別の結果を使って描画する。

Web画面には、Excelでなじみのある表形式の入力、範囲の貼り付け、並べ替え、絞り込み、Excelへの出力も組み込める（構想）。さらに、金融業務に合わせて、一覧から明細へ進み、入力を変え、その影響を表とグラフで追う操作を一つの画面にまとめられる。こうした操作の流れを業務に合わせて設計することで、Excelに匹敵する一覧性を持ちながら、評価結果の根拠まで追いやすいGUIを作れる。
